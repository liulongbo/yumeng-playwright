## 8. 问题与修复

### 8.1 平台 504 被误判为契约变更（已修复）

- **表现**：第 10 位达人采集时，`spread` 请求返回 HTTP `504`，响应体为 `text/html`。采集器在检查状态码前先检查 `content-type`，抛出 `PLATFORM_PAGE_CHANGED:RESPONSE_CONTENT_TYPE`，整任务在 9 位有效达人后 `FAILED`。
- **定位证据**：`.runtime/evidence/failure/b94d146b-98f5-41ee-8041-77f2b042d9d2/3716348dbae140b06121b6b4b7e6d31fff001dac7a755e462f8bb85eb0681640.json`：`status_code=504`、`content_type_kind=text`、`request_key=spread`、`failure_reason=PLATFORM_PAGE_CHANGED:RESPONSE_CONTENT_TYPE`。截图：[LIVE-01-failure-504-2026-10-21.png](assets/LIVE-01-failure-504-2026-10-21.png)。
- **根因**：网关/限流类 HTTP 错误是瞬态传输问题，不是平台契约失效；原实现把它归入不可恢复的 `PLATFORM_PAGE_CHANGED`。
- **修改**：
  - `backend/src/xingtu/observer.py`：`read_response` 在 JSON content-type 检查前，对 `408/500/502/503/504` 抛出 `MODULE_COLLECTION_FAILED:PLATFORM_HTTP_5XX`，让 Engine 按模块级失败隔离并继续。
  - `backend/tests/contract/test_observer.py`：新增 `test_gateway_timeout_is_a_module_failure_not_a_contract_change`，断言 HTML 504 产生 `PLATFORM_HTTP_5XX` 模块失败且 `global_error is None`。
- **验证**：`pytest backend/tests/contract/test_observer.py -q` → 17 passed；全量 `make test-contract` → 34 passed；`make test-unit` → 303 passed；`ruff`、`ruff format --check`、`mypy backend/src/xingtu/observer.py` 通过。真实重试在修复后从 9 位补齐到 10 位并进入终态；本轮未再次自然复现 504，因此真实 504 的“隔离后继续”只由契约测试和重试成功间接支撑，未用人为注入 504 伪造验证。
- **遗留风险**：5xx 现在会留下模块级缺口并可能使任务 `PARTIAL_COMPLETED`；不会自动重试同一模块。是否需要对 5xx 做有限次模块级重试，属于后续可靠性优化。

### 8.2 API 与 Worker 封面目录不一致（已修复运行配置）

- **表现**：前端达人详情封面全部 404，控制台 24 条错误；`media_objects` 与文件实际存在。
- **定位**：Worker 单元配置 `covers.directory=.runtime/covers`，文件数 4565；API env `XINGTU_COVER_DIRECTORY=.runtime/local-main/covers`，文件数 0。API 的 `GET /api/tasks/{id}/covers/{object_id}` 因找不到文件返回 404。
- **修改**：将 `.runtime/local-main/env` 的 `XINGTU_COVER_DIRECTORY` 对齐到 `/Users/Longbo/Developer/YUMENG/.runtime/covers`，重启 API；未改业务代码、未移动/删除封面文件。
- **验证**：登录后 `GET /api/tasks/b94d.../covers/cover/b94d.../f1a684...` → `200 image/webp 237612 bytes`；UI 复测 `IMAGES_LOADED=9/9`、`CONSOLE_ERRORS=0`。
- **遗留风险**：这是本机 local-main 运行配置；若切换到单机 Compose，应统一 `XINGTU_COVER_DIRECTORY` 与单元 `covers.directory`（或改用 S3），否则会再次 404。

### 8.3 契约 breaker 关闭 `search` 后任务无法检索（已按审计方式恢复）

- **表现**：首次提交在 3 秒内 `FAILED: CONTRACT_SCOPE_DISABLED:search`，0 位达人。
- **定位**：`contract_capability_health` 中 v11 `search` 在 17:19 变为 `DISABLED`，`distinct_subject_count=4`，全部失败原因为 `SEARCH_RESPONSE_FAILED`。四次失败任务的 plan 均为 `keyword=户外` + `connection_users.connected.min=10`、`target_count=20`，来自此前非验收脚本把第一个 `input[type=number]`（连接用户数下限）误填为 10，用户本轮真正的需求只有关键词和 10 位。
- **处理**：保存恢复前 breaker 快照到 `.runtime/local-main/contract-breaker-before-reset.json`，执行项目既有命令：
  `xingtu enable-contract --registry contracts/douyin_xingtu.verified.json --actor qa-live-01 --scope search --reason "四起 SEARCH_RESPONSE_FAILED 均来自同一非验收计划（脚本误将连接用户数下限填为 10，非用户需求）；失败证据已保存，现仅恢复 search 作用域以执行关键词唯一条件的受控真实验证"`
  该命令写入 `audit_logs`；恢复后关键词唯一条件的真实检索立即成功（20 位候选）。
- **遗留风险（未修复）**：带 `connection_users` 等筛选条件的路径在本次失败中表现异常（4 次均为 `SEARCH_RESPONSE_FAILED`，而同一状态下关键词检索与 MCP 手工检索均正常）。高度怀疑是动态筛选自动搜索与最终点击搜索产生的重复请求被采集器判为 `RESPONSE_UNCORRELATED`，但本轮未再发起第二条真实采集任务（LIVE-01 明确排除），因此**未确认、未修复**。建议后续用一次受控的带筛选小样本任务定位，并补契约测试；在此之前不要把“带连接用户数筛选的真实采集”标为已验证。

### 8.4 采集中途 lease 丢失并自动恢复（未修复，非阻塞）

- **表现**：17:44:08 单元释放/心跳停止，任务在 17:49:17 变为 `WAITING_FOR_RESOURCE`、`failure_reason=LEASE_LOST`，已保存 7 位有效达人；工作流在 17:51:16 自动重试，17:54:14 恢复 `COLLECTING`，最终补齐到 10 位。
- **定位**：`execution_units.last_heartbeat_at=17:44:08`；期间 `media_objects` 最后写入时间 17:43:55；租约 TTL 120 秒、心跳间隔 15 秒。高度怀疑单个达人/封面下载的长时间操作阻塞了事件循环或心跳，但本轮没有抓取阻塞时的线程栈，**根因未证实**。
- **影响**：任务未丢数据、自动恢复并完成；但长采集存在 lease 丢失和等待放大的可靠性风险。
- **建议**：为心跳增加独立线程/进程或缩短单次外部 I/O 上限；补充长耗时单达人/封面下载的故障注入测试。本轮未改动这部分代码。

### 8.5 API 重启后登录 503（环境问题，已修复）

- **表现**：为应用封面目录重启 API 后，`POST /api/auth/login` 返回 503。
- **定位**：API env 期望 Redis 密码 `localdevredis`，但运行中的 Redis `requirepass` 为空；`redis-cli CONFIG GET requirepass` 为空。
- **处理**：`redis-cli -p 56379 CONFIG SET requirepass localdevredis`；随后登录 200，封面 200。
- **说明**：这是本机 local-main 运行态不一致，不是业务代码缺陷；如果 Redis 被其他方式重启，需同步密码或 API env。

### 8.6 `completed_at` 在重试后仍显示首次终态时间（未修复，UX）

- 页面「完成时间」显示 `10/21 17:33`，而最终更新为 `18:05`。`completed_at` 保留首次进入终态的时刻（`test_completed_at_only_moves_on_the_transition_into_a_terminal_state` 明确覆盖此行为）。状态本身正确，但对“重试后完成”的用户会误读。
- 未改代码：该行为有既有集成测试约束，改动会影响“首次完成时间”的语义；建议另立卡片决定 UI 是否显示“首次完成时间/最近完成时间”。
