## 1. 背景与问题

### 1.1 一句话说明

当前任务失败后只有一个「重试失败步骤」，它同时承担了「补数量」和「补资料」两件事，导致用户只想补 1 位达人时，系统却先去重访 80 位已经入库的达人。

### 1.2 用户看到的现象

举个真实形态的例子：

- 任务目标：100 位达人；
- 执行中断时：19 位资料完整、80 位已入库但部分资料缺失、1 位还没开始采；
- 用户点击「重试失败步骤」后：系统逐个重新打开这 80 位达人的主页，最后才去采第 100 位。

用户的感受是：**等了几个小时，有效达人只多了 1 位；浏览器还被占着，账号也更容易被平台要求验证。**

### 1.3 为什么会这样（业务解释）

系统把「重试」理解成「把所有没做完的步骤再做一遍」，而「没做完的步骤」里同时包含两种完全不同的东西：

- 还差 19 位达人没有采到（**数量问题**）；
- 已有达人缺若干资料模块（**完整度问题**）。

系统目前固定「先补完整度、再补数量」，所以会先处理那 80 位。

同时，页面上「有效入库」和「资料完整」是两个分开的指标，但按钮只有一个，用户**没有办法表达**「我这次只要数量」。

### 1.4 影响

| 维度 | 影响 |
|---|---|
| 时间 | 按历史采集速度（每位达人约 2–4 分钟），80 位约 3–5 小时；而用户真实需要的 1 位约 3 分钟 |
| 账号与线路 | 重复打开 80 位达人主页，产生大量无意义访问，增加触发平台安全验证的概率 |
| 数据 | 每次任务结束都会为**全部**有效达人生成一份新的资料版本，即使内容没有任何变化 |
| 信任 | 用户无法判断「这次重试到底在干什么、做完后发生了什么变化」 |

### 1.5 本轮目标与非目标

**目标**

1. 把「任务没采够、继续采」与「已采够、补资料」拆成两个清晰的业务行为。
2. 没采够时**优先补数量**，本次不重复访问已经入库的达人。
3. 已采够时**只补缺失资料**，不搜索、不新增达人。
4. 用户能看懂：现在有多少有效达人、多少完整、还差几位、还有多少位要补采、这次点击会做什么、做完变化了什么。
5. 不破坏正常首次采集、历史资料版本、分页、人工验证与执行资源机制。

**非目标（本轮不做）**

- 不做任务中心改版、不新增页面；
- 不新增任务类型、不新增任务状态；
- 不改变筛选能力、不改变有效达人标准；
- 不做全自动补采（仍由用户点击触发）；
- 不改达人库结构、不改多角色权限；
- 不改人工验证（安全验证）与浏览器接管流程。

## 2. 用户角色与用户故事

**角色**：媒介人员（一期唯一角色，任务共享）。

| 编号 | 用户故事 |
|---|---|
| US-1 | 任务中断时，我希望系统只把差的达人数量补齐，不要重新跑已经采到的达人。 |
| US-2 | 数量已经够了、但部分达人资料不全时，我希望只补这些达人的缺失资料。 |
| US-3 | 我需要一眼看懂：有多少有效达人、多少完整、还差几位、还有多少位要补采。 |
| US-4 | 我担心重复点击或两个人同时点会重复执行，希望系统保证只执行一次。 |
| US-5 | 我想知道这次重试的目标是什么、结束后到底变了什么。 |

## 3. 术语与口径（先统一语言）

| 术语 | 业务含义 | 用户在哪里看到 |
|---|---|---|
| **有效达人** | 系统在达人主页成功确认「是同一位达人」，且昵称与达人 ID 都读取成功。**其他资料缺失不影响「有效」**。只有达到这个标准才计入目标数量。 | 任务详情「有效入库」 |
| **资料完整** | 任务要求的全部资料模块都读到了结果。平台明确表示「没有这项数据 / 没有权限」算作**已读完**，不算缺失；只有「读取失败」和「本次没有尝试」才算缺失。 | 「资料完整」 |
| **精选完整** | 两组默认精选作品（优秀传播、优秀种草）都完整加载到结尾并读取成功。 | 「精选完整」 |
| **数量达标** | 有效达人数 ≥ 任务目标数。 | 「有效入库 / 目标 100」 |
| **断点续采（继续采集）** | 数量没达标时，保留已有结果，**只补剩余数量**。 | 任务详情按钮 |
| **缺失字段补采（补采缺失字段）** | 数量已达标时，**只补已有达人的缺失资料**，不搜索、不新增达人。 | 任务详情按钮 |
| **失败步骤** | 读取失败、或本次没有执行的资料模块 / 精选集合。 | 「失败步骤」 |
| **资料版本** | 每轮采集为一位达人生成的一份不可修改的数据记录；历史版本全部保留，不会覆盖。 | 达人详情「历史」 |
| **平台未提供** | 平台明确表示该达人没有这项数据。属于「已读完」，不是失败。 | 达人详情字段状态 |

**口径红线（本轮不变）**

1. 有效达人标准不降低，不用「资料凑不齐但算有效」的方式凑数。
2. 筛选条件、排序、目标数量在重试时不可修改。
3. 同一位达人在同一任务中只计一次有效。
4. 平台没有的数据不当作「待补采」，不反复尝试。

## 4. 产品方案总览

### 4.1 两个能力

| | **继续采集** | **补采缺失字段** |
|---|---|---|
| 适用时机 | 有效达人数量 < 目标数量 | 有效达人数量 ≥ 目标数量 |
| 用户目的 | 把数量补齐 | 把资料补齐 |
| 执行对象 | 还没采到的达人 + 后续搜索页 | 已入库但资料不完整的达人 |
| 是否搜索 | 是（沿用原条件、原断点） | **否** |
| 是否新增达人 | 是，且不超过目标 | **否** |
| 是否重访已入库达人 | **否（硬性要求）** | 只访问需要补采的达人 |
| 完成标准 | 数量达标，或平台确实没有更多符合条件的达人 | 所有可补项完成，或确认仍有不可恢复的缺失 |
| 结束后的任务状态 | 已完成（数量够且资料全）/ 部分完成（数量够但有缺失，或平台无更多） | 已完成（补全）/ 部分完成（仍有缺失） |

### 4.2 四条核心原则

1. **数量优先**：任务没采够时，先补数量；本次不碰已入库达人。
2. **能补才补**：数量已够时，只补读取失败或未执行的资料，不重采已经完整的内容。
3. **不动已有成果**：已入库达人、已发布资料版本、断点记录一律保留，不删除、不覆盖。
4. **一次点击只做一件事**：点击时系统明确告诉用户「这次是补数量还是补资料」。

### 4.3 两阶段用户旅程

```
任务中断（执行失败 / 部分完成）
        │
        ├── 有效数 < 目标 ──▶ 【继续采集（还差 N 位）】
        │                        ├── 达标且资料全 ────────▶ 已完成
        │                        ├── 达标但有资料缺失 ────▶ 部分完成（按钮变为「补采缺失字段」）
        │                        └── 平台已无更多符合条件 ─▶ 部分完成（提示新建任务或调整条件）
        │
        └── 有效数 ≥ 目标 ──▶ 【补采缺失字段（M 位）】
                                 ├── 补全 ───────────────▶ 已完成
                                 └── 仍有缺失 ───────────▶ 部分完成（保留原因与已补成果）
```

**说明**：这两个动作是「先后关系」而不是「二选一」。大多数任务会先经历一次「继续采集」，达标后再按需「补采缺失字段」。

### 4.4 与现有能力的关系（复用，不重做）

- 入口仍放在**任务详情页现有操作区**，不新增页面、不改任务中心布局。
- 统计仍用现有 5 张计数卡，只增加副标题说明。
- 失败原因提示仍用现有「任务需要关注」区域，只把文案改成随目标变化。
- 资料版本、历史记录、达人库展示沿用现有规则。

## 5. 功能需求

### FR-1 继续采集（P0）

**触发条件**

- 任务已停止（执行失败，或部分完成），且**有效达人数 < 目标数**；
- 且该任务当前存在可继续的内容（还有未采达人、或可继续搜索）。

**用户操作**

点击「继续采集（还差 N 位）」，二次确认后提交。

**系统行为（业务描述）**

1. 保留已有有效达人、已有资料版本、已有断点进度；
2. 本次只处理「还没有计入有效数」的达人；
3. **不重新打开任何已入库达人的主页**；
4. 如果待采达人不够，就按原筛选条件、从原断点继续搜索（必要时从结果第一页重新核对，但按达人去重，不重复采集、不重复计数）；
5. 采到目标数量即停止，不超采；
6. 任务结束时统一更新状态、统计和资料版本。

**完成标准**

- 有效达人数达到目标；或平台确实没有更多符合条件的达人。

**用户可见反馈**

- 执行中：按钮消失，显示「正在补足剩余达人…」；
- 结束后：
  - 达标且全部完整 → 已完成；
  - 达标但有资料缺失 → 部分完成，并提示「数量已达标，还有 M 位达人资料待补采」，同时按钮变为「补采缺失字段」；
  - 平台无更多 → 部分完成，并提示「平台已没有更多符合条件的达人」。

**验收要点**

- 已入库达人的主页访问次数必须为 0；
- 有效达人数只能增加「剩余数量」，不能重复计数；
- 不改变筛选条件与目标数量。

### FR-2 补采缺失字段（P0）

**触发条件**

- 任务已停止（执行失败，或部分完成），且**有效达人数 ≥ 目标数**；
- 且至少有一位已入库达人存在「读取失败 / 未尝试」的资料或精选。

**用户操作**

点击「补采缺失字段（M 位）」，二次确认后提交。

**系统行为（业务描述）**

1. 不搜索、不扩充达人数量；
2. 只访问存在缺失的达人，只补缺失的资料模块与精选；
3. 已经完整的模块不重新读取，已经完整的精选不重新加载；
4. 平台明确表示「没有 / 无权限」的内容不再补采；
5. 补采成功生成**新的资料版本**，旧版本完整保留；
6. 补采失败时，已成功的资料不丢失，页面如实显示仍缺什么。

**完成标准**

- 所有可补项完成 → 已完成；
- 仍有不可恢复的缺失 → 部分完成，并保留具体原因。

**用户可见反馈**

- 执行中：「正在补采缺失资料…」；
- 结束后：「本次补采已结束：资料完整 X/M 位」，并列出仍缺失的内容类别。

**验收要点**

- 补采过程中不得出现搜索行为；
- 已完整模块的读取时间/版本不得变化；
- 旧资料版本内容逐字节不变。

### FR-3 入口与文案（P0）

- **只保留一个按钮**，按钮文案随本次目标变化：
  - 数量不足：「继续采集（还差 N 位）」；
  - 数量已足：「补采缺失字段（M 位）」；
  - 无法判断时（历史任务/旧版本数据）：「重试失败步骤」。
- 点击后必须弹出二次确认，明确写出「本次会做什么、不会做什么」。
- 不满足条件时**不显示按钮**，并在「任务需要关注」区域说明原因与建议动作。

### FR-4 任务详情的信息展示（P0）

任务详情需让用户在不看日志的情况下回答 5 个问题：

| 用户问题 | 展示位置 | 展示内容 |
|---|---|---|
| 任务完成了吗 | 顶部状态 | 已完成 / 部分完成 / 执行失败 + 一句原因 |
| 采到多少有效达人 | 计数卡「有效入库」 | `99 / 目标 100 · 还差 1 位` |
| 其中多少资料完整 | 计数卡「资料完整」 | `19 · 待补采 80 位` |
| 还有多少要补采 | 计数卡「资料完整」副标题 + 关注区 | 同上一行 |
| 这次点击会做什么 | 按钮 + 确认弹窗 | 明确「补数量」或「补资料」及其数量 |

**重试结束后的变化展示（P0，建议实现方式见 §11 D7）**

- 结束后显示：「本次重试已结束：有效达人 99 → 100，资料完整 19 → 19，仍需补采 80 位」；
- 若暂不保存重试前基线，则至少显示：「本次重试更新了 N 位达人的资料；当前有效 100/100、资料完整 20、待补采 79 位」。
- 展示必须与达人列表、资料版本计数一致，不能出现「页面说补了 5 位、列表只变了 2 位」。

### FR-5 操作可用性（P0）

按钮是否出现、出现哪一个，由服务端判定，前端只负责展示（防止前端误判导致非法操作）。完整矩阵见 §6.1。

### FR-6 防重复与并发（P0）

- 同一次点击重复提交，只执行一次，不产生第二个任务、不产生第二次采集；
- 两位媒介人员同时点击，只有一次生效，另一次提示「任务状态已变化，请刷新后重试」；
- 执行中的任务不显示重试按钮。

### FR-7 历史与留痕（P0）

- 每次「继续采集 / 补采缺失字段」都要留下记录：谁、什么时间、本次目标、执行结果；
- 资料版本只增不改，历史版本永远可查；
- 任务原有的完成时间、创建人、来源任务等历史信息不被覆盖。

### FR-8 完成度与任务状态更新（P0）

- **已完成**：数量达标 **且** 所有有效达人资料与精选都完整；
- **部分完成**：数量未达标，或数量达标但仍有资料缺失；
- **执行失败**：出现不可恢复的异常，任务停止；
- 补采成功后，若所有条件满足，任务可以从「部分完成」变为「已完成」；
- 补采失败不会把任务从「部分完成」变成「执行失败」，只保留原因。

### FR-9 没有可补内容时（P0）

- 没有任何缺失、也没有未采达人：不显示重试按钮；
- 只在关注区说明「当前任务没有需要重试的步骤」。

### FR-10 不可补采项的处理（P1）

- 平台明确没有的数据、无权限的数据：标记为「平台未提供 / 无权限」，**不再推荐补采**；
- 同一达人连续两次补采都没有任何新增资料：在页面上提示「建议使用手动更新或新建任务」，不无限推荐（见 §11 D2）。

## 6. 业务规则与边界

### 6.1 任务状态 × 用户操作矩阵

> 以下均为页面上的中文状态名。「短暂故障自动等待」「等待执行资源」属于系统自动恢复，不提供人工重试。

| 任务当前状态 | 继续采集 | 补采缺失字段 | 取消任务 | 说明 |
|---|---|---|---|---|
| 已接收 / 需求转换中 | 否 | 否 | 是 | 还没开始采集；若需求转换失败，走「修改重提」 |
| 排队中 / 采集中 / 发布结果 | 否 | 否 | 是 | 正在执行，不允许重复操作 |
| 等待登录 / 等待正确账号 | 否 | 否 | 是 | 由登录维护后自动恢复 |
| 等待安全验证 | 否 | 否 | 是 | 人工接管中，不得同时启动第二个浏览器 |
| 等待执行资源 / 短暂故障自动等待 | 否 | 否 | 是 | 系统自动恢复，不提供人工重试 |
| 预算暂停 | **是** | 否 | 是 | 继续执行并按「数量优先」处理 |
| 执行失败（数量不足） | **是** | 否 | 否 | 异常中断后的断点续采 |
| 执行失败（数量已足） | 否 | **是** | 否 | 收口前异常，按补资料处理 |
| 部分完成（数量不足，且有失败步骤） | **是** | 否 | 否 | 例：99/100，80 位资料不完整 |
| 部分完成（数量已足，且有缺失） | 否 | **是** | 否 | 数量已达标，只补资料 |
| 部分完成（平台已无更多达人，且无失败步骤） | 否 | 否 | 否 | 建议调整条件后新建任务，不自动放宽条件 |
| 部分完成（因安全验证终止） | 否 | 否 | 否 | 需先完成人工验证；本轮不提供继续 |
| 已完成 | 否 | 否 | 否 | 由完成标准保证没有可补项 |
| 已取消 | 否 | 否 | 否 | 终态 |
| 需求校验失败 | 否 | 否 | 否 | 仅提供「修改重提」，创建新任务 |

### 6.2 达人状态 × 处理规则

| 达人状态 | 是否计入有效数 | 继续采集时 | 补采资料时 |
|---|---|---|---|
| 只发现身份、还没采 | 否 | **采** | 不处理 |
| 采集到一半中断 | 否 | **重新采** | 不处理 |
| 采过但基础资料无效（无法确认是同一位达人） | 否 | **采**（继续补位） | 不处理 |
| 确认无效（达人不存在 / 身份不符） | 否 | **不再访问** | 不处理 |
| 已入库且资料完整 | 是 | **不访问** | 不处理 |
| 已入库但资料不完整 | 是 | **不访问** | **只补缺失部分** |
| 已入库、本次采集失败但资料完整 | 是 | **不访问** | 不处理（确认完整后直接结束） |
| 已入库、本次采集失败且资料不完整 | 是 | **不访问** | **只补缺失部分** |

### 6.3 资料状态 × 是否补采

| 资料状态 | 是否算「已读完」 | 是否补采 | 说明 |
|---|---|---|---|
| 已读到 | 是 | 否 | — |
| 平台明确未提供 | 是 | **否（永久）** | 不是失败，不应反复尝试 |
| 无权限 | 是 | **否（永久）** | 同上 |
| 无数据 | 是 | **否（永久）** | 同上 |
| 读取失败 | 否 | **是** | 可能是瞬时故障 |
| 本次未尝试 | 否 | **是** | 上次没走到这一步 |
| 整个模块读取不完整 | 否 | **是** | 不能当作完整 |
| 精选没有加载到结尾 | 否 | **是** | 终点未被证明 |
| 精选为空且平台已确认 | 是 | 否 | 已完成检查 |
| 封面未生成 | 否 | **是**（随精选一起补） | 封面可补采 |

### 6.4 边界场景清单

| # | 场景 | 现状（用户视角） | 本轮结论 |
|---|---|---|---|
| 1 | 任务「部分完成」，数量没够 | 只有一个重试按钮，会先补资料 | **本次修复**：改为「继续采集」 |
| 2 | 任务「执行失败」，但已有不少结果还没正式发布 | 结果保留在任务进度里，重试后会发布 | 保持；补充验收：不得丢失已有资料 |
| 3 | 任务「已完成」但资料不全 | **不会发生**：完成标准要求数量达标且全部完整 | 不处理；只做历史数据核对 |
| 4 | 基础资料无效 / 只有达人 ID | 不计有效数，继续补位 | 保持，不降低标准 |
| 5 | 重复点击重试 | 只执行一次 | 保持；补充并发验收 |
| 6 | 第 2 页采集中断 | 保留断点，重试后继续；已采达人不重复采 | 保持；但要接受「会重新核对前面几页」，并单独计量 |
| 7 | 人工验证超时导致任务停止 | 任务停在「部分完成」，不提供继续 | 保持；是否开放见 §11 D5 |
| 8 | 浏览器关闭 / 执行资源异常 | 资源恢复后可继续 | 保持（已有隔离与恢复机制） |
| 9 | 新任务搜到已在达人库的达人 | 视为本任务的有效达人，重新采集一份新版本 | 保持 |
| 10 | 同一达人正在「手动更新」或「定时更新」 | 两个任务各自采集，互不覆盖；当前单执行资源下串行 | 保持；补充并发验收 |
| 11 | 重试前想改筛选条件或目标数 | 不允许，只能新建任务 | 保持，并在页面提示 |
| 12 | 平台没有某字段 | 标记为「平台未提供」，不算失败 | 保持，不反复补采 |
| 13 | 每次任务结束都生成新资料版本 | 即使没有变化也会生成 | **建议修复**（见 §11 D6） |
| 14 | 安全验证终止的任务，按钮不出现 | 前端隐藏，但接口仍可被调用 | **建议对齐**：以页面规则为准 |
| 15 | 补采后「完成时间」 | 仍显示第一次完成的时间 | 保持，界面改称「首次完成时间」（见 §11 D4） |
| 16 | 重试瞬间「失败步骤」数变少 | 系统把待补项标记为「重新排队」 | 保持；文案说明「可重试项由系统判定」 |

## 7. 界面与交互说明

### 7.1 任务详情页结构（沿用现状）

1. 顶部：任务标题、任务编号、操作按钮区；
2. 状态区：当前状态、阶段、一句话说明、进度轨；
3. 关注区：失败原因 / 本次目标说明 / 操作结果提示；
4. 计数卡：已发现、有效入库、资料完整、精选完整、失败步骤；
5. 达人列表：任务内达人及其资料入口；
6. 需求与约束：关键词、目标数量、来源、原计划。

### 7.2 操作区文案

| 场景 | 按钮 | 二次确认 | 执行中 | 结束后 |
|---|---|---|---|---|
| 数量不足 | 继续采集（还差 1 位） | 本次只补足剩余 1 位有效达人，不会补采已入库达人的缺失资料。是否继续？ | 正在补足剩余达人… | 本次重试已结束：有效达人 100/100 |
| 数量已足、有缺失 | 补采缺失字段（80 位） | 本次只为 80 位已入库达人补采缺失资料，不会搜索或新增达人。是否继续？ | 正在补采缺失资料… | 本次补采已结束：资料完整 100/100 |
| 旧任务/无法判断 | 重试失败步骤 | 本次只处理未完成的步骤，已成功的内容不会重复采集。是否继续？ | 正在处理未完成步骤… | 已结束，请查看最新状态 |
| 无需重试 | 不显示 | — | — | 当前任务没有需要重试的步骤 |

### 7.3 状态提示文案

| 场景 | 提示文案 |
|---|---|
| 部分完成 + 数量不足 | 已采到 99/100 位有效达人，还差 1 位。点击「继续采集」只补数量，不会重新采集已入库达人。 |
| 部分完成 + 数量已足 + 有缺失 | 已采到 100/100 位有效达人，其中 80 位资料不完整（读取失败或未完成）。点击「补采缺失字段」只补这些达人的缺失部分，不会新增达人。 |
| 部分完成 + 平台无更多 | 平台已没有更多符合条件的达人（已采到 X/Y 位）。可调整条件后新建任务；本次任务不会自动放宽条件。 |
| 部分完成 + 安全验证终止 | 任务因平台安全验证未完成而停止。请先完成验证；当前不提供重试。 |
| 已完成 | 目标已完成，无需重试。 |
| 补采后仍有缺失 | 本次补采未全部完成：仍有 N 位达人的 M 项资料缺失（读取失败 / 未执行）。已补到的内容已保存。 |

### 7.4 计数卡说明

| 卡片 | 含义 | 本轮调整 |
|---|---|---|
| 已发现 | 本次任务找到的候选达人数（不等于采集成功） | 不变 |
| 有效入库 | 达到有效标准、计入目标的达人数 | 副标题增加「目标 100 · 还差 1 位」 |
| 资料完整 | 有效达人中资料全部读到的数量 | 副标题增加「待补采 80 位」 |
| 精选完整 | 两组精选都完整的有效达人数 | 不变 |
| 失败步骤 | 读取失败 / 未执行的资料模块与精选 | 副标题改为「可补采项由系统判定」 |

### 7.5 不可操作时的说明

按钮不出现时，关注区必须说明**为什么**以及**下一步建议**（新建任务 / 完成安全验证 / 等待资源恢复 / 修改重提），不能只显示一个内部错误码。

## 8. 数据统计与对外口径

| 指标 | 定义 | 展示位置 |
|---|---|---|
| 目标数量 | 任务创建时确定，不可修改 | 计数卡、需求区 |
| 已发现 | 本次任务搜索到的候选达人数 | 计数卡 |
| 有效入库 | 达到有效标准并计入目标的达人数 | 计数卡、任务列表 |
| 资料完整 | 有效达人中资料全部读到的数量 | 计数卡 |
| 精选完整 | 有效达人中两组精选都完整的数量 | 计数卡 |
| 失败步骤 | 读取失败或未执行的资料模块/精选数量 | 计数卡、关注区 |
| 还差 N 位 | 目标数量 − 有效入库（最小为 0） | 按钮文案、计数卡副标题 |
| 待补采 M 位 | 有效达人中资料不完整的达人数 | 按钮文案、关注区 |
| 本次重试变化 | 本次重试期间新增/更新的达人资料版本数，以及有效数、完整数的前后变化 | 关注区（结束后） |

**一致性要求**：页面任一数字都必须与达人列表、资料版本记录一致；不同位置不允许出现两套口径。

## 9. 非功能需求

| 类别 | 要求 |
|---|---|
| 不重复访问 | 「继续采集」不得打开任何已达标达人的主页 |
| 不重复搜索 | 「补采缺失字段」不得发起搜索 |
| 幂等 | 重复点击只执行一次；网络重试不会产生第二个任务或第二轮采集 |
| 并发 | 两人同时操作只有一次生效，另一次提示「任务状态已变化」 |
| 可追溯 | 每次重试有记录：操作人、时间、本次目标、结果 |
| 历史保护 | 资料版本只增不改；旧版本可查；不删除已有成果 |
| 兼容 | 历史任务打开后行为正确，不因本次改动报错 |
| 安全边界 | 不改人工验证、浏览器接管、执行资源隔离规则 |
| 可回滚 | 上线后如异常，可回退到旧行为，已产生数据不受影响 |
| 平台合规 | 不因重试放大访问量；不绕过验证；不放宽条件 |

## 10. 验收标准

### 10.1 业务验收场景

| # | 场景 | 操作 | 期望结果 | 核对方式 |
|---|---|---|---|---|
| AC-1 | 目标 100，已有 99 位有效（其中 80 位资料不完整），1 位未采 | 继续采集 | 只采最后 1 位；80 位主页访问次数为 0；有效数 99→100 | 达人主页访问记录、有效数、达人列表 |
| AC-2 | 目标 100 已达标，其中 80 位资料不完整 | 补采缺失字段 | 不搜索、不新增达人；只补 80 位的缺失部分；完整数上升 | 搜索记录、模块读取记录、完整数 |
| AC-3 | 目标 10，已有 6 位有效 | 继续采集 | 只采剩余 4 位；有效数 6→10 | 访问记录、有效数 |
| AC-4 | 已完成且无缺失 | 页面 | 不显示重试按钮；接口拒绝重试 | 页面截图、接口返回 |
| AC-5 | 基础资料无效 / 只有达人 ID | 继续采集 | 不计有效数；继续补位；无效达人不反复访问 | 有效数、访问记录 |
| AC-6 | 失败后已有结果但资料版本未发布 | 继续采集 | 已有资料不丢失；结束后正常发布 | 达人列表、资料版本数 |
| AC-7 | 第 2 页中断后恢复 | 继续采集 | 已采达人不重复采、有效数不重复增加 | 访问记录、有效数、候选去重 |
| AC-8 | 重复点击 / 两人同时点击 | 连续点击 | 只执行一次；另一次提示状态已变化 | 操作记录、执行次数 |
| AC-9 | 补采时再次失败 | 补采缺失字段 | 已成功资料不丢失；旧版本不变；任务仍为部分完成并保留原因 | 资料版本对比、页面状态 |
| AC-10 | 正常首次采集 | 新建任务 | 行为与现在完全一致 | 回归测试 |
| AC-11 | 手动更新 / 定时更新与补采同时存在 | 触发 | 互不覆盖；资料不出现空值回退 | 达人库当前资料、历史版本 |
| AC-12 | 人工验证 / 浏览器异常 / 执行资源恢复 | 恢复后继续 | 仍能正确恢复，不重复采集 | 恢复记录、访问记录 |

### 10.2 通过标准

1. 上述 12 条全部通过；AC-1、AC-2、AC-6、AC-9 为**红线**。
2. 正常首次采集的既有验收全部通过，行为无变化。
3. 页面数字与达人列表、资料版本记录一致。
4. 历史任务可正常打开与操作。
5. 需求范围内无新增的未解释错误码。

### 10.3 真机验收要求

- 后续经授权后，使用 Playwright + 系统 Chrome，**只允许最小样本（≤3 位达人）**；
- 不得为凑验收数据批量创建真实任务；
- 真机验收只需证明：按钮文案正确、继续采集只采剩余数量、补采不搜索、结束后数字正确。

## 11. 待确认的产品决策

> 以下是与业务语义相关、需要你拍板的事项。已给出推荐与理由，未确认前按推荐执行或暂不实现。

| # | 决策 | 选项 | 推荐 | 理由 |
|---|---|---|---|---|
| D1 | 数量未达标时，是否允许用户**主动选择先补资料** | A. 不允许，系统按数量自动判断（一个按钮）B. 允许，提供第二个入口 | **A** | 同一时刻两个目标互斥；单入口最符合「优先补足数量」，也最不容易误操作。后续确有需要再加 B，不返工 |
| D2 | 平台永久缺失的数据，是否需要「连续两次补采无新增就停止推荐」 | A. 不设上限，靠字段状态区分 B. 设置上限并提示手动更新 | **A（本轮）**，B 记入后续 | 平台未提供/无权限已被识别为「已读完」，不会反复补；设置上限需要额外记录，收益有限 |
| D3 | 「部分完成 + 平台已无更多达人 + 无失败步骤」是否允许原任务再搜一次 | A. 不允许，建议新建任务 B. 允许再搜一次 | **A** | 再搜大概率仍是空结果，白白消耗搜索页请求；重新搜索应属于新的业务意图 |
| D4 | 补采成功再次「已完成」时，完成时间显示哪一个 | A. 首次完成时间 B. 最后一次完成时间 | **A，并把文案改为「首次完成时间」** | 保留审计含义；改成覆盖会丢失「何时第一次完成」的信息 |
| D5 | 安全验证超时导致的任务，是否允许人工继续 | A. 本轮不开放 B. 验证完成后允许继续 | **A（本轮）** | 涉及验证次数、浏览器接管与安全边界，风险高，另立需求 |
| D6 | 是否修复「没有变化也生成新资料版本」 | A. 修复：只有内容变化才生成新版本 B. 不修复 | **A** | 直接满足「不重复发布」；也让「本次重试更新了几位达人」成为真实可信的数字；不影响历史版本 |
| D7 | 「本次重试前后变化」如何呈现 | A. 只显示当前结果 + 本次更新人数 B. 保存重试前基线，显示前后对比 | **A（P0）+ B（P1）** | A 不需要额外存储；B 更直观但需要保存基线，建议下一迭代 |

## 12. 发布与回滚（业务视角）

| 项目 | 方案 |
|---|---|
| 发布范围 | 先在本地/测试环境验证，再用 1 个 `目标 1–2 位` 的真实任务做小样本确认，最后用于日常任务 |
| 灰度观察 | 观察 3 个任务：按钮文案是否正确、继续采集是否只采剩余、补采是否不搜索 |
| 回滚 | 可回退到旧的「重试失败步骤」行为；已产生的有效数据与资料版本不受影响 |
| 数据影响 | 不删除、不覆盖任何历史数据；无数据结构变更（见配套技术方案） |
| 失败兜底 | 若上线后发现异常，先停用新按钮文案与策略，保留旧入口可用 |
