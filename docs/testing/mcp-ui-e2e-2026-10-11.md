## 4. 缺陷清单

### DEF-01（P1，设计缺口）已 `QUEUED` 的任务取消后停在 `CANCELLING`
- **复现**：MCP-UI-08。任务已晋级 `QUEUED` 后在页面取消 → `CANCELLING` v4，`allowed_actions=[]`。
- **原因**：`product_queries.command("cancel")` 只对 `RECEIVED`/`PARSING` 直接落 `CANCELLED`；其余状态置 `CANCELLING`，真正终态化依赖 P2 `worker.dispatch()` 的收尾分支。没有 P2 Worker 时该任务**永久停在 `CANCELLING`**。
- **影响**：用户取消后看不到终态；当前实例中 `488eb716`（用户自己创建）、`1489571e`（本轮）均为该状态。
- **建议最小修复**：取消时若该任务尚无任何已投递的采集（`task_dispatches.sent=false` 且无 `collect/*` workflow），说明不存在持有它的采集进程，API 可立即终态化为 `CANCELLED`；否则维持 `CANCELLING` 交 P2 收尾。

### DEF-02（P3，环境观察）API 停机窗口内 UI 出现 500
- **现象**：控制台出现 `GET /api/tasks?limit=20` 与 `GET /api/tasks/{id}` 的 500。
- **证据**：MCP 控制台日志时间为页面加载后 +15.987 s / +16.994 s，正对应我**主动停掉 API 重启**的窗口；同一时段 API 访问日志中**一个 500 都没有**（全部 200），Vite 代理在目标不可达时返回 500。
- **处置**：不是服务端缺陷。排障时应以 API 日志为准；也可考虑把「后端未就绪」与真实 5xx 区分显示。

### DEF-03（P3，工具行为）`browser_wait_for {time: 128}` 未按请求时长等待
- **现象**：请求等待 128 s，实测约 40 s 即返回（`pending_seconds` 从 4.7 增至 45.97 可证）。
- **处置**：超过约 30–40 s 的等待应分段调用，或改用外部计时；不要依赖单次长等待断言时间敏感结论。

### DEF-04（P3，展示）用户主动取消的任务被当作「需要关注」并显示内部代码
- **现象**：终态为 `CANCELLED` 的详情页显示红色「任务需要关注 / TASK_CANCELLED」，页头提示为兜底文案「任务状态已从服务端恢复，页面会按需自动更新。」
- **原因**：`taskMessage` 未覆盖 `CANCELLED`；`failure_reason` 非空即渲染关注面板，未区分**用户主动取消**与真实失败。
- **建议**：`CANCELLED` 使用中性文案（如「任务已按你的操作取消，已持久结果保留」），且 `TASK_CANCELLED` 不进入红色关注面板。

## A.2 采集 Worker 启动即崩溃（DEF-05，已修复）

首次启动 `make collection-worker` 时进程**立即崩溃退出**（exit 2）：

```
temporalio.service.RPCError: workflow execution already completed
  at backend/src/xingtu/worker.py:383  await handle.signal(CollectionWorkflow.wake)
```

- **原因**：`dispatch()` 的取消收尾循环先 `describe()` 判定 `RUNNING`、再 `signal()`；本轮 3 个 CANCELLING 任务的 Activity 在两步之间**已经完成**，对已完成工作流发信号抛错；该异常从 `dispatch()` 冒出并终止 `run_worker()` 的 `while True`，**整个采集消费者死亡**。
- 这是与之前 Intake Worker「派发异常杀死消费者」**同一类缺陷**，只是发生在 P2。
- **最小修复**（`backend/src/xingtu/worker.py`）：`describe`/`signal` 的 `RPCError` 均被处理（工作流已结束则直接终态化为 `CANCELLED`）；`WorkflowAlreadyStartedError` 分支的 `signal` 同样加保护；`run_worker()` 的派发 tick 加兜底，任何 tick 异常只记日志、不再杀死消费者；并为采集 Worker 增加生命周期日志。
- **验证**：修复后 Worker 稳定存活，并成功把剩余 2 个 `CANCELLING` 任务终态化为 `CANCELLED`。

## A.5 运行态观察：会话后台托管的采集 Worker 会被外部 SIGTERM 终止（非缺陷）

真实采集完成后，`make collection-worker` 进程以 `make: *** [collection-worker] Terminated: 15`（**SIGTERM，信号 15**）结束，日志中只有正常启动行，无任何异常堆栈。核对现场：

| 检查 | 结果 |
|---|---|
| 采集是否受影响 | 无。采集工作流 `collect/02c81708…` 已于 16:02:34 `COMPLETED`，任务已到终态 |
| 执行单元 | `state=READY`、`owner=None`、`lease_until=None`、`browser_stopped=True`、`current_root_task_id=None` —— **租约已正常释放** |
| 遗留浏览器 | 无采集用 Chrome 残留（仅在跑的是用户自己的 Chrome） |
| 待处理任务 | 非终态任务 **0** |

结论：这是**外部终止**（本会话的后台任务被回收），不是 DEF-05 那类崩溃；DEF-05 的修复在本轮真实采集中保持有效。

**运维建议**：需要长期运行的采集/需求转换 Worker，应由操作者在自己终端或进程管理器中启动（`make collection-worker UNIT_CONFIG=…`），不要依赖会话内的后台任务；Worker 被终止时租约与浏览器状态会正常回收，重新启动即可继续。
