> 编写日期：2026-09-24。适用于本项目的 AI 编程工具、独立开发者及协作维护者。

## 1. 使用方式与项目事实

### 1.1 开始工作前

1. 阅读本规范、技术方案相关章节、当前任务卡片和前置任务。
2. 检查实际目录、依赖、命令、已有改动及任务状态；不能只凭上次会话的描述判断现状。
3. 确认目标、影响范围、验收项及所需环境，再实施范围内的最小完整改动。

技术方案定义产品和业务契约，本规范定义工程流程，任务卡片定义本次目标、边界和验收条件。卡片不能隐式覆盖业务契约。发现会改变实现行为的冲突时，指出具体冲突及影响，取得明确结论后同步相关文档；不自行选择更宽松的解释。用户明确确认的需求变更应记录原因和影响，并更新有关卡片与方案。

### 1.3 一期范围

- 首期仅启用抖音巨量星图，单家 MCN、单租户、单一媒介角色，用户共享任务及结果。
- 主流程为表单 → 模型转换和确定性校验 → 持久任务排队 → 平台采集 → 按任务查看结果。
- 默认目标为 20 位，允许 1—200 位有效达人；已有达人计入目标并重新采集。
- 支持登录、任务及详情、任务内达人结果、达人库单达人手动更新、按粉丝档位的周期性更新、恢复、执行单元状态和登录维护；三类任务统一进入现有任务中心，共用执行单元池。
- 未获明确需求变更，不增加评分、导入导出、跨任务达人搜索、多角色、商单与联系方式管理、视频下载或其他平台实现。仅保留既有平台适配边界，不提前实现未来功能。
- 项目独立使用用户、数据库、账号、profile、代理和运行资源，不借用其他项目环境。

## 2. 目录与职责边界

以下为当前实际布局。`frontend/` 尚未创建（U01 未选定）；其余目录已存在，初始化按需创建，不为填满目录而生成空模块。

```text
AGENTS.md                 # 开发规范读取入口
backend/                  # API、领域/应用服务、工作流、Activity、Adapter、基础设施
  tests/                  # 单元、集成、契约、故障恢复测试
frontend/                 # 业务页面、API 客户端及前端测试
contracts/                # 平台能力、字段字典、版本化契约及脱敏样本
migrations/               # 应用业务库迁移
deploy/                   # Compose、部署配置及环境模板
scripts/                  # 统一命令的实际实现
tests/e2e/                # 跨服务业务验收
docs/
  agent.md                # 完整开发规范
  tasks/                  # 后续任务卡片默认位置
```

- 后端领域规则与页面、数据库、供应商实现分离；API 负责认证、输入输出和应用服务调用，不堆积采集逻辑。
- 平台定位器、请求知识、字段映射及错误页判定留在 Adapter；通用工作流只依赖领域契约与引用。
- Workflow 负责持久编排，Activity 执行外部副作用；浏览器 Worker 与 API 进程隔离。
- 前端不决定业务状态、合法操作或有效人数；以服务端契约为准，提交仍需服务端校验。
- `contracts/` 只保存必要且脱敏的配置和样本；人工构造夹具明确标识，生产代码不得依赖测试夹具或伪造结果。
- 业务库与 Temporal 持久库使用独立数据库和凭据；业务迁移不顺带修改 Temporal 内部表。
- 决策记录及运维说明放在 `docs/`；出现实际需要时创建，不重复维护多套事实。
- 已有卡片若由用户指定其他位置，沿用其位置和模板，不复制第二份。调整布局必须同步本规范、入口和命令引用。

## 3. 命令契约与选型门槛

### 3.1 命令状态

下表是命令契约。**2026-09-27 状态**：`help`、`lint`、`format-check`、`typecheck`、`test-unit`、`test-integration`、`test-contract`、`test-e2e`、`check`、`migrate`、`smoke-local` 已实现并实测；`dev`、`stop` 已实现（Docker Compose）但**未在本环境实测**（Docker 守护进程未运行）；`setup` 与 `smoke-live` 未实测（安装入口与真实采集；后者还要求已核验注册表，当前注册表仍为 `UNVERIFIED`，`xingtu start` 会以 `UNVERIFIED_REGISTRY` 拒绝）。实际底层命令、环境参数、必需服务及版本登记在 `Makefile`、`scripts/commands.py` 与 `docs/development.md` 第 3 节。运行前检查入口及环境；缺失或未验证时如实报告"未实现/未验证"，不能猜测底层命令并报告通过。

| 计划命令 | 用途与前置条件 | 副作用及边界 |
|---|---|---|
| `make help` | 列出实际已实现命令、参数、前置环境及危险操作提示 | 不更改环境；不能把占位目标列成可用能力 |
| `make setup` | 按已确定工具与锁文件准备本地依赖 | 可安装依赖；不自动升级版本、创建生产用户或连接真实平台 |
| `make dev` | 使用隔离的本地配置启动开发服务 | 不默认启动真实采集或调用付费模型 |
| `make stop` | 停止本项目本地开发服务 | 保留数据库、对象、profile 和持久卷 |
| `make lint` | 检查代码规范 | 只检查，不自动修复 |
| `make format-check` | 检查格式 | 不改写文件 |
| `make typecheck` | 检查后端及已选前端的类型 | 不跳过实际类型错误 |
| `make test-unit` | 验证纯逻辑和领域规则 | 使用模拟依赖，不访问真实平台或付费模型 |
| `make test-integration` | 验证存储、工作流、接口等边界 | 使用隔离测试服务；数据清理仅限测试环境 |
| `make test-contract` | 验证领域契约与脱敏平台样本 | 离线回归；模拟样本通过不等于平台已验证 |
| `make test-e2e` | 验证跨服务业务链路 | 默认使用受控模拟 Adapter 和模型；与实机冒烟区分 |
| `make check` | 汇总 lint、format-check、typecheck 和 test-unit | 任一失败返回非零；不能替代专项验收 |
| `make migrate` | 对明确指定环境执行已审查迁移 | 改变数据库；环境不明拒绝执行，生产变更按授权规则处理 |
| `make smoke-live` | 验证授权真实账号的小样本链路 | 独立显式运行；预先明确账号/单元引用、数量与调用预算，日志不含凭据 |
| `make smoke-local` | 本地阶段验证载体：`UNIT_CONFIG`、`ROOT_TASK_ID`、`XINGTU_DATABASE_URL`，Temporal 本地测试服务器 | 运行**真实** `Activities.collect` 与 `CollectionWorkflow` 并等待终态；仅用于本地验证，不替代生产编排（OPS-01） |

所有测试和检查必须正确传播失败退出码。不得通过跳过断言、吞异常、空测试目标或修改期望值掩盖失败。初始化时将实际底层命令、环境参数、必需服务及版本登记到命令说明，并验证入口能用；已经实现的目标与仍未实现的目标分别标记。

### 3.2 选型规则

前端、会话组件、模型供应商尚未锁定（U01、U03）。依赖管理、测试与静态检查工具、浏览器与工作流组件已锁定，记录见 `docs/decisions/DEC-001-toolchain.md`。开发相关模块前用简短决策记录说明：待解决问题、选择、主要替代方案、与已定架构的兼容性、最小验证结果、版本及限制。影响产品、费用或生产环境的选择先确认必要授权；已有授权范围内的常规工程选择可自主落实并记录。

依赖使用所选工具的锁文件，镜像与浏览器使用经测试的固定版本组合；新增或升级依赖说明必要性。不得使用浮动版本冒充可重现部署，不在本规范中编造未验证的版本号。

## 4. 任务卡片与开发闭环

### 4.1 统一记录来源

任务卡片是开发任务状态、验收事实和交接信息的统一记录来源。聊天记录不能代替卡片更新。这里的“任务”指开发管理任务，与系统中的根采集任务及其运行时状态不同。

后续开发开始前读取对应卡片。缺少卡片时，在已明确授权的范围内补建最小卡片再实施；影响实现的需求含糊时先澄清。默认每张卡片用稳定 ID 命名为 `docs/tasks/<任务ID>.md`，遵循既有编号约定并检查不重复。已有模板沿用原结构，补齐必要字段，不重写无关卡片。

本次仅交付规范与根目录入口，按用户明确范围不创建具体卡片或任务目录。该例外不代表后续开发可以省略卡片。

> **2026-09-26 更新**：任务卡片已建立于 `docs/tasks/`（BASE-01、UNIT-01、F04、F05），总览见 `docs/tasks/README.md`。上一段的"不创建卡片"仅适用于规范首次交付时。

每张卡片至少包含：

| 字段 | 要求 |
|---|---|
| 基本信息 | 稳定任务 ID、标题、状态、带时区的更新时间 |
| 目标与范围 | 预期结果、包含内容、明确不做的事项 |
| 关联与依赖 | 适用 F 功能、T 验收项、U 空缺、前置任务 ID/链接；不适用时写明原因，不强行关联 |
| 验收清单 | 可逐项验证的勾选项；明确仅模拟验证还是包含真实账号验证 |
| 实现记录 | 实际行为、关键改动和文件引用；尚未实施时如实留待完成 |
| 验证证据 | 日期、环境、实际命令、结果、必要的脱敏日志/报告引用；未执行原因及影响 |
| 交接信息 | 阻塞项、遗留问题、下一步；无则明确写“无” |
| 状态历史 | 时间、原状态、新状态和原因；保留原验收及完成历史 |

### 4.2 状态与更新时机

| 开发状态 | 条件 |
|---|---|
| 待办 | 尚未开始 |
| 进行中 | 已开始实现或验证；本轮结束但尚未完成时可保持此状态，并写明下一步 |
| 阻塞 | 必要依赖、信息、资源或授权缺失，无法推进必要工作 |
| 待验收 | 实现和可执行检查完成，仍有要求的实机、环境或人工验收未完成 |
| 已完成 | 所有验收项满足，适用检查通过，证据与卡片均已更新 |

开始工作、发现阻塞、完成重要验证以及本轮结束时回写卡片。解除阻塞后根据实际工作恢复“进行中”或进入“待验收”，并说明原因。缺少账号/设备而不能开展必要实现时标“阻塞”；实现已结束、仅等待实机验收时标“待验收”。

范围变化需要同步验收条件并保留变化原因及确认依据。不得删除失败项、降低原验收标准或将未执行标记为“不适用”来获得完成状态。已完成任务的原验收缺陷需重新打开对应卡片，改为进行中或阻塞并保留历史；新增需求另建卡片关联原任务。

### 4.3 每项任务的执行顺序

1. **读取与定位**：确认方案、卡片、前置任务及实际工程现状。
2. **影响分析**：定位受影响模块、公共契约、迁移、工作流历史和测试，识别真实平台核验需求。
3. **实现**：围绕验收项完成最小完整改动，避免顺手重构；保留用户和其他任务的已有改动。
4. **验证与自查**：运行适用检查，检查失败路径、数据一致性及范围；只在新增变化或未解决风险需要时补充测试。
5. **回写与交接**：更新卡片、必要方案/契约/决策记录，按证据决定状态，再给出最终回复。

范围内常规实现和修复直接推进；产品范围变化、破坏性数据操作、新增付费资源及生产发布需要明确授权。已有明确授权不重复申请。卡片不得被用作未经授权部署或删除数据的依据。

已有 Git 仓库与 GitHub 远程（见 1.2 节）；沿用既有流程推送分支，先检查工作区再变更，不覆盖他人修改，不提交密钥、profile 或未脱敏证据。提交应聚焦单一任务并关联任务 ID；不能编造提交号、分支或 PR。

### 4.4 完成后强制回写

**强制要求：AI 每次完成开发、执行自动测试或取得测试结果后，必须主动回写任务文档，不等待用户提醒或再次确认。开发 → 测试 → 根据证据更新验收项和状态 → 同步进度文档 → 最终回复，是一个不可省略的交付闭环。** 自动测试包括命令行、浏览器自动化、MCP 及其他测试工具；只负责测试或验收的后续会话同样承担回写责任。具体执行规则见第 4.5 节。

结束任务前逐项执行：

- [ ] 更新验收清单，只勾选已有证据支持的项目。
- [ ] 写入实际实现结果、关键改动与文件引用。
- [ ] 记录实际命令、环境、结果和证据；未执行项记录原因及影响。
- [ ] 设置真实状态与更新时间，追加必要状态历史。
- [ ] 保留阻塞、遗留问题及下一步；新增工作另行记录，不混淆当前任务边界。
- [ ] 同步 [任务索引](tasks/README.md) 和 [项目任务进度总览](项目任务进度总览.md) 的状态、统计、阻塞及下一步；验收事实只在卡片及其引用的证据维护。
- [ ] 最终回复给出卡片链接、状态和未完成事项。

**未回写卡片，不满足交付 DoD。** 无法写入卡片时，说明原因并列出待回写内容，不宣称交付闭环完成。不要在聊天中报告“已完成”而卡片仍为“进行中”，也不要先写“已完成”再等待必要测试。

交付回复至少包含：实现结果、关键改动、验证结果、卡片链接及状态、未完成事项。涉及 API、数据模型或工作流变化时补充兼容性、迁移和恢复影响。

### 4.5 自动测试 MCP／工具与任务进度联动（强制）

本项目采用“AI 开发 → 自动测试 MCP／工具验证 → AI 自动回写任务进度”的工作方式。**执行开发或接收测试结果的 AI 是回写责任主体**，不能假定测试工具会修改 Markdown，也不能把更新文档留给用户。此规则不依赖某个特定 MCP；接入新工具后同样适用。规则本身不代表已安装测试工具或部署了后台监听服务。

#### 4.5.1 开发与测试的执行闭环

1. **绑定任务**：开始开发或测试前，确认任务 ID、对应卡片和本次适用验收项；读取最新状态，避免覆盖其他会话更新。一次测试涉及多张卡片时，分别记录结果及影响，不批量标记完成。
2. **开发结束立即记录**：回写已实现内容、关键文件、尚未覆盖的验收项和拟执行的测试。开发完成但适用测试尚未执行或仍在运行时保持“进行中”，不能提前标“已完成”。
3. **获取实际测试结果**：调用已接入的 MCP／工具，确认测试确实执行并取得结束状态及报告。异步工具仅返回已提交、运行 ID 或启动成功时，记录“测试中”，不能据此判断通过；运行 ID、报告位置和待检查事项写入卡片，供后续会话继续。
4. **逐项判定并回写**：每批相关测试结束后，及时把通过、失败、跳过、未执行或结果不明确映射到卡片验收项。仅勾选证据覆盖且满足完整验收条件的项目；单个用例或部分环境通过不代表整项通过。发现影响已有验收结论的回归时，撤销受影响勾选、保留原历史并重新打开任务。
5. **修复与复测**：范围内可修复的失败继续修复并运行相关复测；保留初次失败、修复和复测记录。不能删除失败记录、降低断言、跳过失败项或反复重跑直至偶然通过来获得完成状态。
6. **同步并交付**：按第 4.2 节更新卡片状态、是否验收、带时区的更新时间及状态历史，再同步任务索引和项目总览中的相关行、状态统计、阻塞和下一步。回读确认一致后，才发送最终回复；回复指出更新的卡片、测试结论、当前状态和剩余事项。

#### 4.5.2 测试证据的最小记录

卡片的“验证证据”至少包含：

- 测试日期、执行环境与模式（离线／合成、真实本地浏览器、生产线路等），以及实际测试的代码版本或改动范围；无 Git 时注明关键文件和测试时间，不编造提交号。测试后又修改相关代码时，原通过结果不能自动覆盖新改动，应补适用复测。
- MCP／工具名称与实际命令或调用动作、相关验收项／T 用例；适用时记录工具运行 ID、契约／Adapter／模型版本。
- 实际结束状态、退出码或工具等价结论，以及报告提供的通过／失败／跳过数量；工具未提供的信息如实注明，不补造统计。工具调用成功不等于业务断言通过。
- 可追溯且脱敏的报告／日志／截图引用；重要结论和必要证据存入 `docs/evidence/` 并从卡片引用，不能只依赖聊天记录或可能失效的临时报告链接。不得复制凭据或未脱敏平台原文。
- 失败、未执行、跳过或结果不明确的原因、影响、修复／复测结果及下一步。工具不可用、环境未就绪或结果丢失必须记为验证缺口，不能记为通过。

#### 4.5.3 状态判定与分阶段交接

| 实际情况 | 必须回写的开发状态 |
|---|---|
| 代码仍在开发；测试未开始、运行中或失败后仍可继续修复 | 进行中；写清实现进展和待验证／修复项 |
| 必要工具、环境、信息或授权缺失，导致必要开发或测试无法继续 | 阻塞；记录具体阻塞、影响及解除条件 |
| 实现及当前可执行检查已完成，仍等待要求的实机、目标环境或人工验收 | 待验收；列出尚未满足的验收条件，不把离线通过当成实机通过 |
| 卡片全部验收项满足、适用检查通过、证据齐全且进度文档已同步 | 已完成；记录完成依据，无需再让用户手动确认改状态，除非卡片明确要求的人工验收尚未完成 |
| 已完成任务出现影响原验收的回归 | 重新打开为进行中；必要条件缺失无法推进时为阻塞，保留原完成与回归历史 |

“是否验收”与验收清单同步：完整验收前不得写“是／已验收”；部分通过注明验证层级和剩余项。工具使用的“测试中／通过／失败”等是测试结果，不新增或替换第 4.2 节的开发状态。

开发与测试分两次会话进行时，开发会话必须先写入明确的测试交接：任务 ID、已改文件、验收范围、实际可用测试入口、所需环境、待执行项及当前状态。后续测试会话读取卡片，执行测试、获取结果并直接更新同一卡片和两个总览，不另建重复进度文档。仅收到外部工具结果时，还须确认其测试对象、版本、环境和验收覆盖是否对应当前任务。

尚未收到外部异步测试结果时，只记录待跟进状态，不承诺无人值守自动更新。结果被后续会话或已配置的自动化接收后，接收方必须完成上述回写。文档无法写入时必须明确报告回写失败及待补内容，不能宣称任务已完成。

## 5. 工程实现约束

### 5.1 契约与代码规范

- 遵循技术方案第 13—16 章的领域类型、API、状态和错误分类。API 输入输出与版本化载荷使用明确 Schema，不用任意 JSON 掩盖缺少定义的单位或语义。
- 公共接口或类型调整需同步调用方、Schema、契约样本和相关文档；明确旧数据、检查点及工作流历史的兼容方式，不能静默改变行为。
- 使用职责清楚的模块与类型注解，沿用既有命名和工具检查规则。错误不能被宽泛捕获后伪装成功；全局异常、局部失败和字段缺失分开处理。
- 日志携带适用的 root/task/attempt/unit 标识，记录可行动原因，不输出秘密或未经筛选的平台正文。资源、监听器和页面在结束或异常时释放。
- 新增数据库约束及迁移说明数据影响和验证方式；不以直接修改生产表代替受控迁移。

### 5.2 模型与平台契约

- P1 输出声明式 `FilterPlan`；确定性校验覆盖每个已填字段的类型、范围、枚举、单位、组合及语义。不能丢字段、额外加条件、近似替换或用空条件降级搜索。
- 模型不输出选择器、Cookie 或工具代码，生产中不允许模型自由点击或执行任意代码。模型记录保留版本、用量、耗时和错误，不保存隐式推理及凭据。
- 能力、请求、字段和页面契约版本化。未知端点、参数、定位器、枚举及来源明确留空并标记 `UNVERIFIED`；仅经核验的能力可标记 `VERIFIED` 并启用，失效能力标记 `DISABLED`。
- 响应观察先注册再触发操作，并验证页面、条件、身份、模块、分页及周期归属；不能只按 URL 片段或最后返回时间取数。HTTP 200 登录 HTML、业务错误和未知 Schema 不能解析成空列表。
- 固定 sleep 不替代就绪与终点证据。搜索分页、虚拟列表和持久候选队列按方案处理；无进展不等于耗尽，基础资料事务落库后才计有效人数。
- 浏览器响应与登记 DOM 为既定路径；可选接口调用默认关闭，通过等价性、会话、线路及失败恢复验证后逐项启用。禁止猜测接口或通过验证码绕过、签名逆向、随机 UA、代理轮换替代已定方案。

### 5.3 数据与精选作品

- 只采集 `excellent_reach` 和 `excellent_seeding` 两个默认精选模块，保留组内顺序和独立观测。不固定四条或 Top X，不按发布时间筛选，不进入全量列表，也不采集响应中越过模块范围的作品。
- 同作品可复用已验证身份，但两组归属、顺序及指标独立保存；无法取得身份时保留局部卡片，不能按标题或昵称合并。
- 字段状态使用 `COLLECTED`、`NOT_PROVIDED`、`NO_PERMISSION`、`NO_DATA`、`FAILED`、`NOT_ATTEMPTED`。真实零值与缺失分开；“找不到元素”不能直接视为平台未提供。
- 保存原文、单位、精度、金额币种/合作形式、周期、来源及观测时间；金额使用 Decimal，缩略值保留近似/下界语义。不补造副标题、链接、发布时间或周期标签。
- 达到人数不代表采集完整；两个模块覆盖、字段失败、未执行及缺口必须参与完整性判断。恢复时集合变化生成新观测，不拼成虚假的同一时点列表。
- 封面允许受控下载入对象存储，不下载视频、不用 OCR 编造业务字段。先验证上传对象，再提交引用，未引用对象按受控规则清理。

### 5.4 任务、持久化与恢复

- PostgreSQL 保存任务、启动意图、幂等事实、快照、检查点和租约；Redis 仅用于可重建缓存和限流。
- 创建需求、根任务和工作流启动意图使用同一事务；确定性 workflow ID 防止重复启动。幂等请求同键同内容返回原结果，同键不同内容报冲突。
- 取消、重试、继续验证状态及版本；预算暂停、人工等待、资源等待不作为终态。区分发现数、有效数和完整数，不把暂停伪报为搜索耗尽。
- Workflow 不执行不可重放外部 I/O，Activity 承担副作用并具有幂等性；大结果、候选列表和证据留存储中，工作流传递引用。
- 检查点与对应结果事务提交；发布快照不可修改。任务内查询必须读取关联快照，不能以达人最新投影替代历史数据。
- 手动/定时更新创建新根任务，不执行搜索或 P1、不改变旧任务人数和快照；更新任务在统一执行单元池中按 `allowed_task_kinds` 认领，正常采集优先。周期只在“新快照 + 身份有效 + `pipeline_complete`”后重置，部分更新不重置。
- 写入检查尝试版本、租约代次及任务状态，拒绝旧尝试和取消后的迟到提交。当前投影仅接受较新且有效的观测，失败和无权限不清空旧值。
- 自动重试遵循方案预算，不在解析器、客户端和 Activity 层叠加无限重试；页面契约失效、登录和安全挑战不盲重试。工作流变更必须验证历史重放或明确兼容策略。

### 5.5 执行单元、安全与运维

- 一个执行单元绑定一个账号、线路/代理端点及独立持久 profile，并发为 1。人工维护与采集互斥，不共用日常浏览器目录，不跨进程同时打开 profile。
- 租约到期不等于浏览器停止；确认终止旧执行者或撤销其访问后才能重新分配，不能确认隔离则置为 `QUARANTINED`。数据库拒绝旧代次不能替代浏览器隔离。
- 平台请求及 DNS 走绑定线路，线路/隧道断开禁止回落直连或其他账号线路。登录后验证账号、受保护页面及线路，更新会话版本并销毁旧观察器再恢复。
- 凭据只传受控引用，不写入普通配置响应、模型输入、日志、卡片或版本库。原始 HAR/Trace 默认关闭，受控诊断临时启用、隔离原件，仅保留经检查的脱敏摘要。
- 认证保护业务 API 与封面，执行任务关联检查；同角色共享权限不取消审计。下载限制来源、重定向、类型、大小及超时，禁止任意地址读取。
- 业务快照及引用封面默认持续保留，不能随缓存或临时证据清理。具体默认值以技术方案附录 A 为准，不把保护预算写成 SLA。
- 上线前验证迁移、工作流兼容、真实账号冒烟、异机恢复及旧节点隔离；发布和恢复有操作记录及运维手册，未验证的 RPO/RTO 不作承诺。

## 7. 验证策略与 DoD

### 7.1 按影响选择验证

技术方案第 18 章 T01—T42 为验收依据。卡片选取适用项并补充本次回归；不机械要求每次运行全部测试，不用无意义覆盖率或重复实现的测试代替行为证据。

| 改动类型 | 必要关注点 |
|---|---|
| 领域/模型条件 | 完整字段覆盖、范围、单位、错误枚举、不支持条件及模型失败；参考 T01—T04 |
| 任务/存储 | 幂等、事务失败、启动响应丢失、并发操作、取消、迟到写入、预算与恢复；参考 T12—T16、T19、T21 |
| Adapter | 身份、操作响应关联、Schema、分页终点、候选顺序、单位和来源冲突；参考 T31—T40 |
| 精选集合/快照/刷新 | 范围、分组、历史不可变、集合变化、字段缺失和失败不清空旧值；参考 T06—T11、T24—T29、T41 |
| 认证/资源/部署 | 认证和封面访问、独占维护、线路与 DNS、旧节点隔离、备份恢复及证据脱敏；参考 T17—T20、T22、T30、T40、T42 |
| 纯文档 | 引用与术语、方案一致性、命令真实性、范围和可操作性；无需伪造应用测试结果 |

模拟样本、脱敏实机样本和真实账号验证分别标识。记录验证日期、环境、契约/Adapter 版本及结果；样本验证通过不能代替当前平台可用性验证。无法运行的检查写清原因、影响和后续步骤，不勾选通过；测试失败后修复原因，不削弱断言。

### 7.2 分层完成定义

| 层级 | 必须满足 |
|---|---|
| 开发任务完成 | 卡片全部验收项满足；适用检查通过；相关文档、契约和卡片已回写；实际证据可查；无影响原验收的遗留缺陷 |
| 功能验收完成 | 对应 F 功能和适用 T 用例通过；异常和恢复已验证；影响该功能验收的 U 空缺已核验解决，其他相关缺口如实记录 |
| 生产上线就绪 | 影响上线的 U 项已验证关闭；真实账号冒烟、线路隔离、迁移与工作流兼容、备份恢复及必要运维检查通过 |

卡片范围若明确仅为领域接口和模拟测试，可以在满足该范围后完成，但不能将依赖实机的整项功能标为完成。卡片包含真实采集验收时，缺少账号或设备保持待验收或阻塞。

**代码写完、页面能打开、模拟测试通过均不能单独证明真实采集可用；卡片未回写也不能报告开发任务交付完成。**
