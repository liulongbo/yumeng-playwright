# DEC-019：任务级重试按「补数量 / 补资料」拆分（不新增任务类型与 Schema）

- 日期：2026-10-24
- 状态：已实施（2026-10-24）
- 关联：RETRY-01；产品需求 [RETRY-01 PRD](../prd/RETRY-01-retry-and-backfill.md)；技术方案 §8.1、§14.5；[任务中心架构](../任务中心架构.md) §6.8

## 待解决问题

一个「重试失败步骤」同时承担两种用户目标：补足达人数量、补全已有达人资料。命令层把
`retryable` 候选（含「已计入有效数但模块未完成」的达人）全部置回待采，引擎又固定先处理
「已有效但未完成」的候选，导致 99/100 场景先重开 80 位已入库达人的主页，最后才采第 100 位；
每次任务收口还会为全部有效达人生成新快照，即使内容没有变化。历史证据见
[QA-01 重试语义核验](../evidence/QA-01-retry-semantics-2026-10-24.md) 与 DIAG-01 ISSUE-006。

## 选择

- 由任务自身计数派生重试目标（不存储新字段、不加任务类型）：
  - `valid_count < target_count` → **继续采集**：只恢复「尚未计入有效数」的候选；已计数达人
    若停留在 `pending`（上一次重试的遗留）收敛为 `done`，本次不再访问；`collecting` 的已计数
    达人由引擎完成（原有断点恢复行为）。
  - `valid_count >= target_count` → **补采缺失字段**：只恢复「已计数但不完整」的候选；未计数
    候选一律不重新入队，避免失败步骤计数无故下降。
- 策略集中在新模块 `retry_policy.py`（纯函数），产品 API 与内部 CLI 共用，避免两套实现漂移。
- 产品详情新增只读 `retry_plan`（目标、还差数量、待补采数量、上次重试时间、上次重试后更新
  人数）；数据来自既有 `audit_logs` 与 `creator_snapshots`，**无迁移、无 payload 字段**。
- 补采时若两组默认精选已完成则跳过重载；终态收口只对内容有变化的达人生成新快照。
- 安全验证终态（`SECURITY_CHALLENGE_*`）在命令层与页面规则对齐，直接调用接口同样拒绝重试。

## 主要替代方案

- 增加显式 `retry_scope` 请求参数与两个按钮：需要新协议字段、幂等键维度与更多 UI，且同一时刻
  两个目标互斥；本轮不做（PRD D1=A），保留后续扩展位。
- 新增任务类型「补采任务」：会产生新根任务、破坏「同一业务任务补采」语义，且需要迁移与列表改造。
- 在 `root_tasks.payload` 或 `Candidate` 增加策略/基线字段：两者 `extra="forbid"`，新增字段会使
  旧代码无法读取回滚后的 payload；因此改用派生策略 + 只读查询。

## 影响

- 重试语义变化：未达标时不再补采已入库达人的缺失资料，需在数量达标后再点一次补采。
- 审计动作变为 `retry:continue` / `retry:backfill`（原 `retry` 行仍被查询兼容）。
- 正常首次采集行为不变（首次不存在「已计数且待采」候选；精选跳过条件不成立）。
- 回滚安全：无 Schema、无 payload、无 Workflow 变更，回退代码即可；已重试到一半的任务新旧代码
  都能读同一份 checkpoint。
