# DEC-009：真实采集策略与平台验证（反爬）处置

- 日期：2026-09-28
- 状态：已采纳（本地阶段执行中）；部分结论待实测

## 待解决问题

本地阶段真实采集时观察到两件事，需要明确策略并留档：

1. **登录状态**：浏览器重启后会话入口页仍显示登录表单，容易被判断为"登录没保存"，需要说清"保存了什么、什么情况下必须人工重登"。
2. **平台验证（反爬）**：进入达人主页时平台下发了文字点选验证码。需要明确当前采集策略是什么、是否"解决"，以及遇到验证时的既定行为。

## 事实与证据（2026-09-28 02:2x，本地阶段）

- **登录状态确实落盘且持续续期**：`unit-local-mac-02` 的 profile cookie 库包含 `sessionid`/`sid_tt`/`sid_ucp_v1`/`uid_tt`（到期 2026-11-27 02:27:46，即本轮浏览器使用期间被平台续期）、`passport_auth_status`（2026-10-27）、`sid_guard`（2027-09-23）；`Cookies` 文件最后写入 02:29:01。单元状态 `READY`、`session_version=4`。
- **会话入口页与应用会话不是同一个域**：入口是 `sso.oceanengine.com/xingtu/login?role=1`，该页总是渲染手机号+验证码表单；应用侧会话（`www.xingtu.cn`）有效时，应用壳会自行加载。因此"看到登录表单"≠"已登出"。
- **平台会失效服务端会话**：2026-09-27 13:57 曾实测到 `/u/api/user/info` 返回 `用户未登录`，此时必须人工重登。
- **验证码确实被触发**：02:28:42 打开达人主页时出现 iframe `https://rmc.bytedance.com/verifycenter/captcha/v2`，内容为"验证码／依次点击文字"，请求号 `2026092802284286336642743A042D8AD4`；同轮 `verify.zijieapi.com/captcha/get` 被调用。
- **该轮业务接口未被阻断**：同一次观察中 `get_author_base_info`、`get_author_spread_info` 均返回 `base_resp.status_code=0`（Success），基础字段正常读取。
- **未证明安全**：没有证据表明"验证出现时所有数据面都不受影响"；报价/联系方式等更敏感的数据面是否被验证门控**未核验**。触发原因很可能与自动化节奏有关（数秒内 market → 搜索 → 详情连续跳转），而 `action_interval_seconds=2.0` 只是保守值，平台限流阈值**未实测**。

## 选择（当前采集策略）

按技术方案 §13.4/§13.5 的既定路径执行，**不引入任何绕过手段**：

1. **网络与身份**：显式 `network_mode`。本地阶段 `local_development`（本机 IP、无代理、不伪造线路证明）；生产 `production_line`（代理 + `NetworkProof` + 探针，`production-preflight` 拒绝本地单元）。真实账号 + 项目独立持久 profile（`0700` 目录、`0600` 文件锁、单进程独占、禁与日常浏览器共用）。
2. **会话引导**：先访问 `session.entry_url` → 有界等待应用壳就绪（`protected_ready`，`session_boot_timeout_seconds=180`）→ 再进搜索入口；账号身份与 `expected_account_id` 精确比对，不一致报 `WRONG_ACCOUNT`。
3. **并发与节奏**：单执行单元、单账号、单 profile、**并发 1**；搜索页与详情页在同一 BrowserContext 内串行打开/关闭，不做多标签并行；动作间隔 2 秒（保守）；搜索只取首页（`single_page_only`）。
4. **采集路径**：浏览器真实交互（填关键词 → 点搜索按钮 → 点达人卡片），**不调用平台私有接口、不构造请求、不逆向签名**；动作前注册 `request/response` 监听，按方法+主机+路径+请求体绑定关联响应，归属不唯一即判读取失败，不取"最近一次响应"。
5. **字段范围**：只采注册表声明过的字段（当前 `basic` 9 个），值来自授权会话内的真实响应，并记录 `source_kind`/`path_ref`/`observed_at`/`session_version`/契约版本；平台空串记 `NO_DATA`，不臆造。
6. **遇到登录失效或安全挑战**：映射为 `ACCOUNT_LOGIN_REQUIRED` / `PLATFORM_SECURITY_CHALLENGE`，任务进入**等待人工**状态，**不盲重试**、不换 IP、不伪装客户端；人工在维护窗口完成后继续（一期由 F10 承担）。
7. **失败与恢复**：租约 + 检查点 + 不可变快照；失败证据脱敏落库；恢复只重采不完整模块；达到目标即停；预算用尽记 `PAUSED_BUDGET`，不谎报"平台已耗尽"。

## 主要替代方案与否决理由

- 自动识别/绕过验证码、注入隐身脚本、随机 UA、代理轮换：方案 §13.4 明确禁止（"不引入 Selenium/隐身驱动、签名逆向、随机 User-Agent、代理轮换或移动端替代采集路线"），且会破坏"真实账号 + 已验证契约"的验收前提。
- 放弃浏览器主路径、直接复现平台私有接口：接口与签名未经验证，属猜测，且 §13.4 要求接口优化默认关闭、逐项等价性验证后才可启用（`direct_api_enabled=false`）。
- 提高并发或缩短间隔"抢数据"：会放大风控概率，也与"单单元并发 1"和不放大访问量的要求冲突。

## 影响与限制

- **"解决反爬"不是本项目的目标，也不会以绕过方式实现**；可做的是：降低触发概率（节奏、跳转次数、单次时长）、把挑战做成可观测状态、由人工在维护窗口处理。
- 未实测：平台限流阈值与允许访问节奏；验证被触发时具体哪些数据面被拒；挑战 iframe 的稳定定位（尚未登记进契约，因此当前只能靠超时兜底，不能立即判定"遇到挑战"）。
- 登录状态是"浏览器会话 + 服务端会话"，**不是永久免登**：服务端失效时必须人工重登；生产由 F10 的受控远程维护解决。

## 最小验证与下一步

- 已验证：登录 cookie 落盘与续期（cookie 库 + 到期时间）、单元 `READY`/`session_version=4`、4 次 `xingtu login` 与两次应用引导在无人工干预下通过、真实采集 2 位达人落库（[证据](../evidence/UNIT-01-real-collection-2026-09-27.md)）。
- 下一步（合规缓解，按收益排序）：
  1. 登记验证挑战 iframe 的定位与分类，使任务在挑战出现时**立即暂停并提示人工**，而不是靠超时。
  2. 实测访问节奏上限（在人工观察下逐步加大间隔），形成结论写回契约的 `action_interval_seconds`。
  3. 记录"第 N 位达人触发验证、当时读到哪些字段/被拒哪些"，形成数据面门控的实测结论。
  4. 由 F10 落地人工登录/验证的维护窗口与会话版本更新。
