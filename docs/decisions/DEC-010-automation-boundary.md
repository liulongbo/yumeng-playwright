# DEC-010：自动化边界与登录/验证编排

- 日期：2026-09-28
- 状态：边界已采纳（不可自动化部分明确排除）；编排实现待 F10
- 关联：技术方案 §11（F10）、§13.4、§17.1、附录 B；开发规范 §5.2、§7；[DEC-009](DEC-009-crawl-strategy-and-anti-bot.md)

## 待解决问题

用户目标：**自动登录 → 自动验证 → 自动采集并入库**（尽量减少人工）。需要先确认其中哪些部分可以在本项目既定安全边界内实现、哪些必须由人完成，避免实现出一个违反方案约束、且会危及账号与合规的"全自动"方案。

## 冲突点（必须显式登记，不得自行放宽）

| 依据 | 原文要求 | 对"自动验证"的影响 |
|---|---|---|
| 技术方案 §17.1 | "只使用授权账号可访问的能力；**平台验证码、设备验证或访问限制进入人工处理，不通过技术绕过**" | 自动通过验证码 = 技术绕过 → **禁止** |
| 技术方案 §11.2（F10） | "**验证码与设备验证保留人工操作**" | F10 的既定设计就是"人工处理 + 自动继续" |
| 技术方案 §11.1（F10） | "在任务需要登录时处理平台扫码或验证，**随后自动继续**" | 自动化目标是"编排与续跑"，不是"代过人机验证" |
| 附录 B | `ACCOUNT_LOGIN_REQUIRED`=等待人工登录，成功验证后自动续跑；`PLATFORM_SECURITY_CHALLENGE`=等待人工验证，**不自动绕过** | 遇到挑战的正确行为是等待，不是重试或绕过 |
| 开发规范 §5.2 | "禁止猜测接口或通过**验证码绕过、签名逆向、随机 UA、代理轮换**替代已定方案" | 同上 |
| 技术方案 §13.4 | 不引入 Selenium/隐身驱动、签名逆向、随机 User-Agent、代理轮换 | 同上 |

结论：**"自动验证"（机器代替人通过平台人机验证）不可实现，也不应尝试**。手机短信验证码同属"平台验证码"，同样进入人工处理范围。

## 选择（合规范围内的最大自动化）

把目标改写为可验收的形式：**无人值守运行 + 仅在平台要求人机验证时人工"一触"介入，随后全自动续跑**。

1. **零登录优先（会话保活）**：只要服务端会话有效就不登录。措施：定期轻量保活、稳定出口与设备指纹（生产阶段即 J1900/蜂窝线路的固定出口）、单账号单并发、保守访问节奏、减少页面跳转、只取必要页面；并在会话临近失效前主动进入维护窗口，而不是等失效。
2. **挑战可观测化**：登记验证挑战的定位与分类（如 `rmc.bytedance.com/verifycenter/captcha/v2` 的文字点选、短信码表单、限流提示），使任务在挑战出现时**立即暂停并给出可行动原因**，不再靠超时兜底；映射到 `ACCOUNT_LOGIN_REQUIRED` / `PLATFORM_SECURITY_CHALLENGE`。
3. **维护会话编排（本次自动化的主体）**：发起维护 → 取得独占维护租约（与采集互斥、限时 15 分钟）→ 打开受控浏览器（U06 远程承载）→ 自动定位/准备登录入口与手机号输入（凭据只经受控引用，不落日志）→ **人工输入短信码或完成点选** → 自动提交 → 自动校验三项证据（账号一致 / 受保护页面可用 / 线路正常）→ `session_version++`、销毁旧观察器 → 幂等唤醒等待中的工作流，从检查点续跑。
4. **通知与一键入口**：挑战出现时通过受控渠道通知人（本地通知/控制台/IM），人工只需点击一次链接完成验证；维护超时可重新打开，业务任务不被取消。
5. **采集与落库全自动**：契约内的搜索、候选发现、主页模块采集、字段解析、事务落库、快照发布、恢复重采均为自动，无需人工。
6. **指标化（用于验收替代"全自动"）**：验证触发率（每 N 位达人触发一次）、平均无人工连续运行时长、单次人工维护耗时、维护后自动续跑成功率。

## 主要替代方案与否决理由

- **自动识别/代过验证码（含打码平台、模型识别）**：违反 §17.1 与 §13.4，且会显著提高封号与合规风险；否决。
- **OTP 自动接收（自有 SIM + 短信转发自动填报）**：短信码属"平台验证码"，§17.1/§11.2 要求人工处理；且自动填码需要跨域读取验证码表单与短信通道，属绕过式自动化；否决。**若用户坚持要求**，须走正式变更：用户明确授权 → 更新技术方案 §11/§17 与开发规范 → 评估平台服务条款、账号风险与审计要求 → 记录新决策及影响，不能由实施方自行放宽。
- **隐身指纹/随机 UA/代理轮换提高通过率**：§13.4 明确禁止；且会破坏"真实账号 + 已核验契约"的验收前提；否决。
- **靠缩短间隔、加大并发"抢数据"**：放大风控概率，违反单单元并发 1 与不放大访问量的要求；否决。

## 影响与限制

- 验收口径变化：**不得承诺"完全无人值守"**；改为验收"无人值守 + 人工一触 + 自动续跑"及其指标。
- 责任归属：本工作由 **F10** 承接实现；UNIT-01 提供会话/单元/租约/会话版本原语；OPS-01 提供部署、调度与通知通道；远程承载方案仍属 U06。
- 未实测：验证触发率与允许访问节奏；挑战是否门控特定数据面（报价/联系方式）；U06 远程承载选型。
- 本地阶段仍只能人工：`xingtu login` 打开本机浏览器、人工完成验证。

## 最小验证（实施时需取得）

1. 会话自检：不开人工窗口即可判断应用会话是否有效（引导 + `protected_ready` + 账号比对），并在失效时给出明确状态。
2. 挑战检测用例：正样本（真实出现挑战时立即暂停并给原因）与反样本（正常页面不误判为挑战）。
3. 维护编排端到端：独占互斥（采集期间不可维护、维护期间不采集）、限时超时、错误账号拒绝、成功后等待任务从检查点自动续跑。
4. 指标采集：至少记录一次"挑战出现 → 通知 → 人工完成 → 自动续跑"的完整时间线证据。
